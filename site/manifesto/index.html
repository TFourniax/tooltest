SPHAIRA PAPER 01
September 2026

A Sphaira Lab manifesto

The 20th Prompt Problem.

The first prompt creates momentum. The twentieth inherits a system that neither the builder nor the agent can fully hold in mind.

Contents

01

The first prompt feels like leverage.

Describe the thing. Watch the files appear. See an interface take shape before the coffee cools.

For the first time, software creation is available to people who never planned to become software engineers. That is not a toy. It is a redistribution of productive power.

Developers feel it too. The empty file is no longer the expensive part. Agents can draft migrations, tests, integrations and refactors in minutes. The distance between intent and a plausible implementation has collapsed.

But plausible is doing more work in that sentence than we admit.

02

Then comes the twentieth prompt.

The system now contains decisions nobody explicitly remembers making.

One prompt added authentication. Another repaired a redirect. A third changed the data shape to make the screen render. Five prompts later, the workaround has become an assumption. Ten prompts later, that assumption is load-bearing.

The builder sees a product that still runs. The agent sees the context currently available. Neither sees the full chain of accepted compromises, missing checks, incidental edits and interactions that accumulated along the way.

Generation compounds output. It does not automatically compound understanding.

This is the 20th Prompt Problem: each new instruction operates on a larger inherited system while the human’s ability to explain that system grows more slowly than the system itself.

03

A green check is not institutional memory.

Tests answer the question they were written to answer. They do not tell you whether it was the right question.

When an agent writes the implementation and its tests in one trajectory, “all tests passed” can be reassuring without being discriminating. The new test may also pass on the old code. The intended fix may depend on only two of six edits. Two individually removable edits may still back each other up.

None of this makes tests useless. It makes their boundaries important.

The honest question is not “is the code safe?” in the abstract. It is: what did this selected executable evidence establish about this exact change, in this environment, under this budget?

Anything stronger is theatre.

04

Control must compound with autonomy.

The faster a machine can change a system, the more legible its boundaries and consequences must become.

Control cannot mean asking a human to inspect every generated line. That simply recreates the old bottleneck after accelerating everything before it.

It also cannot mean asking another language model for a confidence score. One model’s persuasive explanation is not an independent experiment on another model’s patch.

Useful control has four timescales. During the session, prevent a small class of clearly dangerous actions. Before acceptance, interrogate the actual change with executable evidence. At explanation time, translate without upgrading uncertainty. After merge, preserve the obligations that convenience created.

These layers should reinforce each other without pretending to be interchangeable.

05

We are building an instrument, not an oracle.

An instrument exposes a signal, its provenance and its limits. An oracle asks to be believed.

DiffWitness is our first instrument. Protect can observe or stop supported high-confidence actions, but its findings remain observations. Proof runs controlled experiments on the bound Git patch. IdleProof changes the language, not the facts. The Debt Ledger keeps obligations alive until a matching check says they were repaid.

The system is designed around a refusal: OBSERVED, SUGGESTED and UNKNOWN may never be cosmetically promoted to VERIFIED.

That refusal is not defensive copy. It is the product.

06

The future we want is not slower. It is more accountable.

We want founders to build software they can understand. We want developers to delegate without surrendering evidence. We want agents to move quickly inside boundaries that remain human-owned.

AI coding will not wait for perfect verification. It should not. The opportunity is too large.

But speed without memory turns every future prompt into an excavation. Speed without evidence turns every green check into a leap of faith. Speed without explicit debt quietly borrows from a maintainer who may not exist yet.

Software written by machines needs instruments made for that reality.

More autonomy. More control. Both, or neither lasts.
