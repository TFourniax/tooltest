# PM-002 — Durable tasks and change association

## Acceptance contract recorded before implementation

Preserve the existing cross-runtime native task ID and temporary prompt context.
Persist only the task identity, prompt digest/length, session digest and ordinal
by default. Raw prompt, truncated anchor, session identifier and current focus
must not enter durable ProjectEvents, checkpoints or the derived database.
Explicit user-authored task labels/reasons are opt-in durable declarations.

Native prompt submission records each task once and records its participation in
the exact armed native boundary. A fresh boundary gets a fresh identifier. Short
follow-ups keep the same task; explicit pivots preserve all participating tasks.
Task activation is an OBSERVED hook fact, not evidence that the task is complete.
The successful native handoff associates its exact change with those recorded
participants. Session co-occurrence is not executed causal Proof; use a distinct
OBSERVED `worked_on` edge, while an explicit human `motivates` relation remains
DECLARED. Neither operation upgrades the task or its link to VERIFIED.

Task declarations, descriptions, activations and links use a typed profile.
References must point to earlier compatible records in the same validated
journal. Reject missing/cross-task/cross-boundary references atomically. Do not
rewrite the existing change artifact or its dedupe identity to add a task.
Journal, checkpoint and cache validation must agree.

Provide public add/describe/link/show commands, durable history and related
change/evidence retrieval after the temporary session is deleted. Context
lookup by an explicit title/reason or task ID must retrieve linked changes
without inventing semantic text from hashes. Preserve old envelopes, schema
versions, Proof acceptance and provider Stop behavior.

## Required gates

Regression-first public/native privacy and identity cases; native multi-task
association with real Proof; retries/idempotency; references and authority;
checkpoint/rebuild and cache validation; Guided/Technical and installed command
journeys; full platform/package/benchmarks/integration and fresh exact-main.
Record failures and fixes. MACHINE is separate from HUMAN. Required human
provider/release scenarios remain unqualified until a human executes them in
real conditions on the applicable candidate.

This Core unit does not silently claim complete IdleProof/Portal task UI or
shared-context consumer adoption. Their acceptance is tracked separately in
PM-002/010/013 and must be closed before the full coordinated release gate.

## Implementation and review

The additive `project-memory-task-1` profile validates four event types. All
journal/checkpoint admissions validate references in order. Native task links and
the existing change/proof/debt import append atomically. Task declaration and
activation are separate idempotent appends; a declaration can survive a failed
activation, which marks the boundary degraded. Edge-only events preserve entity
content/authority. Unprofiled historical extension events retain their semantics.

The context validator stamp changes to invalidate pre-task caches. Context ranks
explicit task IDs and user-saved labels/reasons; digests are not semantic intent.
Guided/Technical and FR/EN commands share the same facts. No new dependency,
network destination or Proof authority is introduced. Existing journal replay
costs remain linear per validation; large-history incremental performance remains
PM-012, not an unmeasured claim of this change.

Privacy is producer-bound: native writes use a strict field whitelist. Explicit
descriptions intentionally save user-provided text. The profile and hashes enforce
consistency, not authenticity of arbitrary supplied histories. See TASK_MEMORY.md
for usage and recovery limitations.
